# Практические сценарии

## Перенести локальный макет в тему

Сначала перечисли все отдельные секции каждой страницы макета в порядке вывода. Для каждой страницы прочитай `get_page_structure` (все виджетлисты и экземпляры), выбери контентный виджетлист и вызови `get_page_structure` с картой `expected_sections: [{section,widget_id?,widget_type?,block_template_handle?,libraries?}]`. Секция засчитывается только тогда, когда её ID указывает на видимый экземпляр нужного виджетлиста. `missing`, `extra`, `reordered` и `complete` показывают состав и порядок; `quality_warnings` показывает несовпадение типа, шаблона или библиотеки с явно указанной картой. Разницу библиотеки у существующего слайдера оцени как результат аудита, а не запрос на миграцию. Повтори аудит после каждого размещения; наличие одного только типа виджета секцию не закрывает.

Если макет содержит карту виджетов, сохрани её границы: промо, товарные подборки, FAQ и другие самостоятельные секции должны оставаться отдельными редактируемыми экземплярами. Не заменяй всю главную одним большим виджетом. Перед изменением страницы запиши соответствие секций, экземпляров и виджетлистов.

Прочитай `get_widget_standards` и исходники подходящего типа через `get_widget_type`. Системный виджет можно взять за основу, если его поведение подходит, но разметку нужно привести к макету и удалить неиспользуемые HTML/CSS/JS. Не выбирай системный виджет только из-за похожего названия. Если существующие шаблоны блоков не позволяют разместить нужные картинки, выбери подходящий шаблон из каталога или добавь его в платформу.

Если нужен готовый системный виджет, найди его через `list_system_widget_types`, затем прочитай `get_system_widget_type`. По умолчанию каталог возвращает поколение 4; для поколения 3 передай parameters.generation=3. Это каталог типов; `list_widgets` и `get_widget` показывают установленные экземпляры. Создай экземпляр через `create_widget` с `widget_list_id` и `widget_type_id`. Дополнительного применения нет. Не перебирай числовые ID и не угадывай маршруты.

Для анимированной бегущей строки дождись загрузки шрифтов и проверь движение, расстояние между фразами и стык повторов на ширинах 360, 390 и 1440 px; отсутствие горизонтальной прокрутки страницы само по себе не выявляет наложение текста. В отчёте отдельно укажи, что подтверждено чтением API, действием в браузере и визуальной проверкой. При добавлении вариантов не вычисляй размерные характеристики из соседнего размера без источника; допущения по остаткам называй явно.

Для новой секции подготовь код, при необходимости проверь его локально через `inspect_widget_source` и покажи diff через `diff_theme_values`. Создай тип через `create_widget_type`, затем экземпляр через `create_widget` с полученным ID типа и целевым виджетлистом. Это отдельные записи; при ошибке сообщи результаты выполненных шагов. Изображения загрузи через `create_store_file` с обёрткой `file`, затем используй ID файла в блоке. Исходники из локальных файлов можно прочитать через `read_widget_sources`; JSON-поля передаются объектами.

Стили карточки товара держи в каждом типе виджета, которому они нужны. Общий сниппет или CSS создавай только по явному запросу. Разметку фильтра адаптируй к макету, сохранив платформенные URL, параметры и действия. Если в макете слайдер поддерживает стрелки или свайп, проверь их действием. Для новой секции выбери подходящую доступную библиотеку или реализуй требуемое поведение в `snippet.js`. Существующий слайдер не переписывай на TvistV1 без явной просьбы пользователя: сначала исправляй текущую реализацию. Получи публичную ссылку через `get_theme`; она содержит `theme_preview=<id>` даже при подключении MCP к staging. Сравни главную, каталог и карточку со скриншотами макета при 360, 390, 768, 1440 и 1920 px, проверь фильтры, варианты, корзину и слайдер действием в браузере. Перенос завершён только при `complete=true` для каждой карты секций и пройденной визуальной и функциональной проверке. `get_page_structure` проверяет отдельный виджет в ограниченном контексте `page`; страницы каталога и товара проверяй на настоящей витрине.

## Создать секцию темы как виджет

Предпочтительно используй `create_widget_type` для создания типа и видимого экземпляра одной атомарной командой Theme Editor. `update_widget_type` и `create_widget` сохраняются для независимого управления типом и экземпляром. Страница должна выводить `widget_lists.<handle>.widgets`; `update_theme_asset` используй для общих шаблонных файлов и сниппетов.

## Добавить настройку цвета виджету

Прочитай settings-reference и core-css-reference в widget-architecture. Получи пользовательский тип, изучи settings_form, settings_data и SCSS. Добавь настройку в существующую структуру и свяжи её со стилями через принятые в виджете CSS-переменные. Почему: поле интерфейса само по себе не меняет цвет.

Если выбран конкретный существующий экземпляр, подготовь один `update_widget_type` с согласованными полями. `update_widget_type` используй только когда пользователь намеренно меняет самостоятельный пользовательский тип для всех его потребителей. Проверь JSON и SCSS. После записи проверь редактор. Изменение default не означает обновление всех существующих экземпляров.

## Изменить описание товара

Найди товар, прочитай description и revision. Передай только нужные текстовые поля в update_product. Почему: отправка всей карточки могла бы изменить цены или варианты. Результат — повторно прочитанное описание соответствует запросу.

## Устаревшие данные и кеш

Прочитай liquid-widget-cache-keys и реальный Liquid. Определи зависимости блока и версии, уже входящие в ключ. Ключ должен отражать зависимости содержимого; случайная строка или массовый сброс не объясняет причину.

Проверь widget_basic_cache_key и account.*_basic_cache_key по справочнику. Кешируй фрагмент вывода коллекций или меню, а не весь виджет, если остальная разметка зависит от пользователя, URL, фильтров или текущего состояния страницы. Не придумывай поля Liquid. Инструментов сброса Redis/серверных кешей нет.

## Создать страницу доставки

Проверь по списку, что страницы ещё нет, затем вызови `create_page` с title и content. После записи прочитай страницу. Для ссылки в меню сначала прочитай меню и его пункты, затем вызови `change_menu_item`.

## Ответить без магазина

На вопрос о различии типа и экземпляра виджета ответь через search_knowledge/get_knowledge_section. Подключение магазина не требуется. Отдели объяснение платформы от непроверенного состояния конкретного магазина.

## Изменить код существующего или системного виджета

Если пользователь указывает существующий виджет, прочитай его через `get_widget`. Для поиска по атрибуту data-widget-drop-item-id используй `list_widgets` с `parameters.list_item_id`: это ID вхождения в список. Системный тип сначала выдели через `make_widget_custom`; затем измени код через `update_widget_type` с `expected_updated_at`, равным прочитанному `updated_at` типа. Другие экземпляры пользовательского типа могут разделять его код — при требовании изменить только один сначала выполни `make_widget_custom` и для него.

Сначала получи `theme_id` через `list_themes`. Если известен только класс widget-type_{handle}, найди кандидатов через `list_widgets` с `widget_type_handle`. Не подставляй ID типа вместо ID экземпляра; при нескольких кандидатах уточни нужный экземпляр.

Не создавай отдельный theme asset и не добавляй inline-скрипт в layout как fallback. Такая правка обходит границу экземпляра и может повлиять на другие страницы. Layout допустим только для явно глобального поведения или после отдельного согласования. После применения проверь код, новый `widget_type_id` там, где требовалась копия, а также неизменность settings и list_items.

## Изменить существующую настройку экземпляра виджета

Прочитай экземпляр через `get_widget` и найди имя настройки в `widget_type.source.settings_form`. Вызови `update_widget` с `parameters.settings` и `parameters.expected_updated_at`, равным прочитанному `updated_at`. `clear_settings` очищает значение, `reset_settings` возвращает default или убирает переопределение; пересечения ключей запрещены. Запись меняет выбранный экземпляр без копирования типа. `settings_data` типа задаёт значения по умолчанию. При конфликте не подменяй ревизию автоматически.

## Создать категорию каталога

Через `read_content(kind=collection,mode=list)` найди родительскую категорию и убедись, что не создаёшь дубликат. Передай `title` и `parent_id` в `change_collection(action=create)`, проверь результат операции. Для ручного добавления товара в обычную категорию используй `change_collection_membership(action=add)`; это не меняет складскую категорию товара. Удаление доступно только для пустой категории без дочерних категорий и ещё раз проверяется перед DELETE.


## Собственная схема повторяемых блоков

1. Найди схему через `list_block_templates`, прочитай её через `get_block_template`.
2. При необходимости создай схему через `create_block_template`.
3. Создай `BlockListWidgetType` через `create_widget_type` с `block_template_id`; `name` и JSON-поля передаются объектами.
4. Создай экземпляр через `create_widget`. При необходимости передай стартовые блоки через `replace_widget_blocks`.
5. Каждый запрос атомарен отдельно; несколько HTTP-запросов общей транзакции не образуют. При ошибке сообщи выполненные шаги.

Отдельные схемы обслуживают create_block_template,
update_block_template и delete_block_template. Для изменения
передать updated_at из детального чтения как expected_updated_at. Если передаётся fields, это полный
упорядоченный состав: существующие поля сохраняются по id. Без fields меняются
только метаданные. Схема общая для магазина: проверять usage и опубликованные темы.
Для используемых схем разрешены подписи, перестановка и добавление полей;
несовместимую структуру создавать новым шаблоном. Удаление возможно только без
зависимых блоков, списков и типов виджетов. После execution_unknown сначала
сверить состояние; не создавать новую операцию записи автоматически.
